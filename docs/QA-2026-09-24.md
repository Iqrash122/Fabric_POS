## Vendor payment behavior

Open **Vendors → Pay vendor** beside a vendor, or use the toolbar's **Vendor payment** button.

1. **Pay outstanding balance** settles opening payable, then posted unpaid bills ordered by bill date and ID. Only debt dated on or before the payment is eligible.
2. **Pay a specific bill** settles the chosen vendor's unpaid posted bill. Selecting it fills the unpaid amount, which can be edited for partial payment.
3. **Advance payment** explicitly records money on account. It does not reduce an unrelated bill automatically.

The amount paid leaves the selected Cash / Bank ledger account once. Excess above the eligible balance remains an advance. Existing advance and return credit are applied through **Advance / credit**, without recording another cash payment. Existing payments are not automatically reallocated.

The form shows payable, advance and return credit; filters inactive vendors/accounts; clears bill and amount when the vendor changes; and clears amount, bill and note after success. Cash is the default when an active cash account exists. Recent vendor payments show reference, vendor, date, account, amount, amount applied, remaining advance and note.

Browser reconciliation example: two bills totaling 200.00 → payment 125.00 → payable 75.00 → payment 100.00 against the remaining bill → payable 0.00 and advance 25.00. A separate explicit 30.00 advance brought the total cash deduction to 255.00. Each balance and history update was asserted.

## Repeat locally

PHP tests (SQLite extensions are not enabled in this machine's default PHP configuration):

```powershell
php -d extension=pdo_sqlite -d extension=sqlite3 vendor/bin/phpunit
php vendor/bin/phpstan analyse --no-progress --memory-limit=1G
npm run types:check
npm run build
```

For browser tests, set `APP_ENV=testing`, `DB_CONNECTION=sqlite`, and an absolute `DB_DATABASE` pointing to the separate browser database before invoking `scripts/qa/seed-browser.php`. The seed script recreates that database and refuses non-testing databases without `browser` in their name. Set `FABRIC_TEST_CREDENTIALS` to a local credential-file path. Start the isolated server with `scripts/qa/browser-router.php` and SQLite extensions enabled; then run Playwright with `FABRIC_TEST_URL=http://127.0.0.1:8765`, `FABRIC_TEST_BROWSER_CHANNEL=chrome` and the same credential-file path.

Browser evidence is in `test-results/browser-results.json` and `test-results/vendor-payment-mobile.png`. Test result files are replaced on subsequent runs.
